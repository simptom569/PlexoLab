# Работа без связи, уведомления, поиск

Решения владельца 2026-10-26 (все запросы утверждены). Этапы Н1–Н5 в `docs/PLAN.md`. Всего этого нет в макете: новые элементы собираются только из переменных `design/styles.css` и стилей окна «Настройки».

## 1. Работа без связи (Н1, Н2)

### 1.1 Что считается «связи нет»

Связи нет, если выполнено любое из двух:

- запрос к серверу не дошёл (`NetworkError`) или ответ 502, 503, 504 (сервер за прокси не отвечает);
- живое соединение (WebSocket) закрыто и не удалось подключиться заново.

Связь есть, когда любой запрос получил ответ сервера (даже 4xx) или WebSocket дал `ready`. Пока связи нет, клиент раз в несколько секунд проверяет `GET /healthz` (без токена, вне `/api/v1`), а также при событиях `online` и возвращении окна на передний план. Настройка «Обновлять вживую» выключена: WebSocket не работает, остаются запросы и проверка `/healthz`.

### 1.2 Режим «только просмотр»

Включается, когда связи нет **3 секунды** подряд (короткий сбой Wi-Fi не должен мигать блокировкой). Выключается сразу, как связь вернулась. После возвращения клиент перечитывает все запросы.

Пока режим включён:

- сверху рабочей области полоска «Нет связи с сервером. Можно читать, править получится, когда связь вернётся.» Если есть неотправленный текст страницы или документа, добавляется «Неотправленные правки сохранены и уйдут сами.»;
- закрыты правки: перенос карточек и страниц, поля задач, комментарии, создание, чекбоксы, редакторы текста и холст, загрузка файлов, удаление. Читать, открывать задачи, переходить по экранам, фильтры, вид, тема, настройки приложения доступны;
- любой запрос на запись, который всё же дошёл до клиента API, отклоняется сразу, без сети (`OfflineError`), экран откатывается, всплывает короткая плашка;
- экраны не подменяют содержимое надписью «Не удалось загрузить…», пока данные есть; ошибка показывается только если данных нет совсем;
- плашка «Не удалось сохранить страницу» при обрыве не всплывает (говорит полоска).

Вход при обрыве не теряется: токен обновляется только по ответу 401. Полноэкранное «Сервер не отвечает» бывает только при запуске приложения.

### 1.3 Тексты страниц и документов

Черновик, набранный до обрыва, остаётся в памяти, не теряется и уходит после возвращения связи сразу (не ждёт 5 секунд). Дальше обычный путь: 409, слияние как в git, а при настоящем столкновении:

- человек на этой странице: прежняя плашка `ConflictBanner` («Страницу изменил другой участник»);
- человек ушёл со страницы: **копия рядом**. Его правки сохраняются отдельной страницей (документом) «Название (правки Имя, дд.мм чч:мм)» у того же родителя (в том же проекте) сразу после оригинала, оригинал остаётся с чужой версией, всплывает плашка «Правки не удалось объединить, они сохранены отдельной страницей». Если разошлись только названия, копия не нужна: остаётся чужое название.

Холст сохраняется целиком, последнее сохранение побеждает (прежнее решение, отдельной защиты нет). Задачи, модули, релизы и ссылки версий не имеют, побеждает последний.

### 1.4 Защита при закрытии приложения

Если в окне есть неотправленный текст, при закрытии приложение сначала пробует отправить его пару секунд. Не вышло: спрашивает «Есть неотправленные правки, закрыть?».

## 2. Уведомления и @упоминания (Н3, Н5)

- Поводов два: человека **назначили исполнителем** (не он сам) и его **упомянули** в комментарии задачи. Другие поводы (новый комментарий в моей задаче, упоминания на вики и в документах) не делаются.
- В комментарии набирается `@`, открывается список участников проекта (только они), выбор подставляет имя. В тексте хранится метка `@[id]` с id человека, а не имя: после смены имени старые комментарии покажут новое. Сервер отдельно сохраняет список упомянутых (`comments.mentions`). Комментарий с меткой не участника проекта, неизвестного id или больше чем 20 меток отклоняется (400). Автору уведомление о своём упоминании не приходит.
- Назначение исполнителем не уведомляет, если человек назначил себя; повторное непрочитанное «назначили» по той же задаче заменяется свежим.
- Уведомления лежат в таблице `notifications` (кому, повод, кто сделал, задача и проект, когда, прочитано ли). Доставка живая: событие `notification.changed` только адресату (`Audience::Users`). Прочитанные старше 30 дней и всё сверх 200 самых новых у человека сервер убирает при создании нового уведомления, фонового процесса нет. Список отдаёт до 100 уведомлений вместе с общим числом непрочитанных; уведомления проекта, из которого человека убрали, и архивного проекта в списке не видны (вернётся, и появятся снова). Ручки: `GET /notifications`, `POST /notifications/{id}/read`, `POST /notifications/read-all`.
- В интерфейсе: пункт «Уведомления» в меню пользователя со счётчиком по образцу окна «Приглашения» и точка у имени (общая с приглашениями); окно со списком, где непрочитанное с точкой, а прочитанное приглушено, и кнопка «Прочитать все»; клик по записи отмечает её прочитанной и открывает задачу на доске её проекта. Тексты безличные («Вас назначили исполнителем», «Вас упомянули в комментарии»): родов у людей приложение не знает.
- Окошки Windows (Н5, вместе с этапом 9, трей и автозапуск): только когда приложение не в фокусе; после запуска «3 новых» одним окошком, а не три подряд. Нужен `tauri-plugin-notification` (согласовать при подключении).

## 3. Поиск (Н4)

- Вход: **Ctrl+K** и пункт «Поиск» в меню пользователя (кнопку в боковом меню не добавляем: она изменила бы видимый эталон).
- Ищет только по названиям, не по содержимому: задачи (название и id вида `WEB-141`), документы (название), страницы вики (название), файлы (имя).
- Обычный поиск подстроки по коротким полям, без `pg_trgm`, без полнотекстового индекса и без расширений на сервере. Кириллица: `lower()` зависит от локали базы (так же у поиска документов, см. README), проверить на настоящей базе.
- Результаты только из доступного: задачи и документы из проектов, где человек участник; вики через общее правило доступа.
- Результат: иконка вида, название, проект. Выдержек из текста нет.
