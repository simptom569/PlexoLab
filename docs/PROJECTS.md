# PlexoLab: проекты, участники и id задач. Как это будет работать

Описание **утверждено владельцем 2026-10-21** (все пункты раздела 9 приняты). Это источник правды для проектного уровня: проекты, участники, приглашения, метки и документы по проектам, ключи id задач. По мере реализации актуальная схема и API переносятся в `DATA-MODEL.md`; этапы П1–П5 описаны в `PLAN.md`.

Пункты, помеченные **[моё предложение]**, владелец принял при утверждении.

---

## 0. Коротко

- Любой человек может создать проект. Создатель становится его администратором.
- В проекте две роли: **администратор** и **участник**. Проект и всё его содержимое видят только участники.
- В проект **приглашают**: админ вводит e-mail существующего аккаунта, человек в приложении принимает или отклоняет приглашение.
- Проекты не удаляются, а **архивируются**.
- **Вики общая** для всех, у кого есть аккаунт (пока нет понятия «команда», раздел 7). **Документы, ссылки и лента свои** у каждого проекта; в ленте открытого проекта также события вики.
- Id задачи зависит от ключей: ключ модуля, если он задан, иначе ключ проекта, иначе `TASK`. Все ключи необязательны.
- Сайдбар в покое выглядит как в макете. Управление проектом — по правой кнопке на строке проекта, новый проект — «+» при наведении на заголовок «Проекты».
- Два новых окна, «Приглашения» и «Архив проектов», открываются из меню пользователя рядом с «Настройки».

## 1. Проекты, роли, участники

### 1.1 Кто что может

| Действие | Участник | Админ проекта | Глобальный админ |
|---|---|---|---|
| Видеть проект и работать в нём (доска, бэклог, модули, релизы, документы, ссылки, лента) | да | да | да, во всех проектах |
| Менять название, цвет и ключ проекта | нет | да | да |
| Приглашать людей, отзывать приглашения, убирать людей, менять роли | нет | да | да |
| Архивировать проект и возвращать из архива | нет | да | да |
| Выйти из проекта | да | да, если не последний админ | |
| Создавать проекты | да, любой вошедший | | |

«Глобальный админ» это человек с флагом `is_admin`. Сейчас сервер этот флаг нигде не проверяет, после этапа 2 он начнёт работать. **[моё предложение]** У глобального админа в сайдбаре все проекты (не архивные), ему не нужно быть участником, чтобы управлять любым.

### 1.2 Приглашения

- В окне проекта (раздел «Участники») админ вводит e-mail. Система ищет **существующий** аккаунт (регистр не важен).
- Нет аккаунта: «Аккаунта с таким адресом нет». Человек уже в проекте или уже приглашён: «Уже в проекте» / «Уже приглашён».
- Создаётся приглашение со статусом «ожидает». При приглашении админ выбирает роль (по умолчанию «Участник»). **[моё предложение]**
- Приглашённый видит приглашение в окне **«Приглашения»**: проект, кто пригласил, роль, кнопки «Принять» и «Отклонить». Приглашение приходит живым обновлением, без перезапуска.
- «Принять» → человек становится участником, проект появляется в его сайдбаре. «Отклонить» → приглашение закрывается; пригласить снова можно.
- Админ видит ожидающих в разделе «Участники» с пометкой «ожидает ответа» и может **отозвать** приглашение.
- Приглашения не истекают по времени, пока их не приняли, не отклонили или не отозвали. Приглашения в архивный проект скрыты. **[моё предложение]**
- **Счётчик:** у пункта «Приглашения» в меню пользователя число **неотвеченных** приглашений. Пока оно не ноль, у имени внизу сайдбара есть точка. Всплывающих сообщений нет.
- **Аккаунты из приложения не создаются** (пока): их заводят командой `server user add`. В будущем люди будут регистрироваться сами (авторизация), а не через админа.

### 1.3 Выход, исключение, последний администратор

- Участник может выйти сам: правая кнопка на проекте → «Выйти из проекта», с подтверждением. Админ может убрать другого человека.
- Имя вышедшего или убранного остаётся на старых задачах (исполнитель), комментариях и в ленте. Назначить его на новые задачи нельзя: в списке исполнителей только текущие участники. Вернуться он может только по новому приглашению.
- **Последний администратор** проекта не может выйти, понизить себя или быть убранным: «Вы единственный администратор. Сначала назначьте другого или архивируйте проект». Иначе проект остался бы без администратора. Если админов двое, любой выходит свободно.

### 1.4 Архив

- Проект уходит из сайдбара, все данные целы. **Удаления проектов нет.**
- Ключи архивного проекта остаются занятыми (внутри этого проекта, см. раздел 4).
- Вернуть из архива может админ проекта и глобальный админ. Где: окно **«Архив проектов»** (список и кнопка «Вернуть»), пункт в меню пользователя рядом с «Настройки».

## 2. Что общее, что по проектам

| Что | Как |
|---|---|
| Доска, бэклог, модули, вехи, релизы | по проекту (уже так) |
| **Вики** и файлы вики | **общие** для всех, у кого есть аккаунт. Твоя формулировка «общая из тех проектов, что есть у пользователя» потребует понятия «команда» (раздел 7), поэтому пока так |
| **Документы** (страница и холст) | по проекту |
| **Ссылки команды** | по проекту |
| **Активность (лента)** | в ленте открытого проекта: события этого проекта **и события вики** |
| Вложения задач | по проекту; в библиотеке файлов видны вложения только моих проектов |
| Метки | **по проекту**: у каждого проекта свой список меток, его настраивает администратор в настройках проекта (раздел 3). Метка другого проекта к задаче не привяжется |
| Список аккаунтов | общий (по e-mail можно найти любого) |

События вики (правка страницы, загрузка файла в вики) уже пишутся без проекта. Лента любого проекта показывает свои события плюс эти.

**Существующие данные.** Все нынешние документы и ссылки переносятся в **первый проект**.

## 3. Интерфейс

Все новые окна собираются из тех же строк, полей, кнопок и аватаров, что в окне «Настройки». Макет `design/` не меняется.

- **Сайдбар в покое** как в макете, но показывает только **мои** проекты (без архивных).
- **Новый проект.** При наведении на заголовок «Проекты» появляется «+». Он открывает окно: название, цвет (из имеющихся: accent / warn / ok), ключ (необязательно).
- **Меню проекта.** Правая кнопка на строке проекта открывает небольшое меню, как меню пользователя:
  - «Настройки проекта» — только для админа;
  - «Выйти из проекта» — для всех, с подтверждением.
  Значка ⚙ на строках нет.
- **Окно «Настройки проекта»:**
  - **Основное:** название, цвет, ключ;
  - **Участники:** список (аватар, имя, роль, «убрать»), ожидающие приглашения, поле «пригласить по e-mail» и выбор роли;
  - **Метки:** список меток проекта (цвет и название), добавить, переименовать, сменить цвет, удалить (с подтверждением «Метка стоит на N задачах»). Метки может настраивать администратор;
  - **Архив:** кнопка «Архивировать проект» с подтверждением.
- **Меню пользователя** (внизу сайдбара) получает два пункта рядом с «Настройки»: **«Приглашения»** (со счётчиком неотвеченных) и **«Архив проектов»**. Оба открывают окна в стиле «Настроек».
- **Форма модуля:** новое поле **«Ключ задач»** (например, `SEO`), в стиле остальных полей.
- **Окно подтверждения** (новое): когда у модуля появляется, пропадает или меняется ключ и в нём есть задачи, показывается «У N задач изменятся id. Продолжить?». То же при смене ключа проекта.
- **Таблица (вид задач):** сортировка по столбцу ID идёт по ключу, потом по номеру.

Пока ничего не наведено и меню не открыто, «+» не виден, поэтому эталонные скриншоты сайдбара остаются как есть.

### 3.1 Как это сделано (этап П3)

- **Где код:** `app/src/features/projects/` (окна и меню), `app/src/lib/project-dialogs.ts` (вкладки, роли, цвета, проверка ключа), состояние открытых окон в `useUi` (`projectDialog`, `projectMenu`), стили `app/src/styles/projects.css`. Всё, что окна берут из макета и «Настроек» (`set-dialog`, `set-nav`, `set-row`, `fields`, `sw-btn`, `seg`), названо теми же классами; новые классы только для того, чего там нет (`.proj-head`, `.proj-add`, `.invite-dot`, `.proj-row`).
- **Узкие окна** (новый проект, приглашения, архив) без вкладок, шириной 560px, высота по содержимому (`height: fit-content`).
- **Ошибки** показываются в окне, где их вызвали, а не общей плашкой; общая плашка только у «Выйти из проекта», потому что окна у этого действия нет.
- **Метки в окне задачи** по-прежнему создаются там же и попадают в проект задачи; переименовать, перекрасить и удалить их может только администратор в «Метки».
- **Исполнители** в окне задачи: участники проекта плюс текущий исполнитель (чтобы не потерять уже назначенного, если его убрали из проекта). Фильтр по исполнителям на доске пока показывает всех: список аккаунтов ограничим вместе с «командой».
- **Что не входит в П3:** поле «Ключ задач» в форме модуля и окно «У N задач изменятся id» (этап П4), документы, ссылки и лента по проектам (этап П5).

## 4. Id задач

### 4.1 Как собирается id

Для каждой задачи по порядку:

1. задача в модуле, и у модуля **есть ключ** → ключ модуля (`SEO-3`);
2. иначе у проекта **есть ключ** → ключ проекта (`PLX-12`);
3. иначе → `TASK` (`TASK-12`).

### 4.2 Правила для ключей

- Ключ **необязателен** и у проекта, и у модуля.
- Формат: 2–6 символов, латиница и цифры, начинается с буквы. Регистр не важен, хранится в верхнем.
- В **разных проектах** ключи могут совпадать (у каждого проекта свой `PLX` и свой `TASK`).
- **Внутри одного проекта** ключи не повторяются вообще: ни между модулями, ни с ключом проекта. Пока у проекта ключа нет, занятым считается и `TASK`.
- Ключи **можно редактировать** в любой момент.

### 4.3 Что происходит с id при действиях

| Действие | Что с id |
|---|---|
| Создали задачу | следующий номер из ряда (модуль с ключом → ряд модуля, иначе ряд проекта) |
| Перенесли задачу туда, где ряд тот же (между модулями без ключей, или «без модуля» ↔ модуль без ключа) | id **не меняется** |
| Перенесли в другой ряд (в модуль с ключом, из него, в другой модуль с ключом) | **новый номер** в новом ряду, прежний id уходит в историю |
| Переименовали ключ модуля или проекта | меняется только подпись, **номера те же** (`SEO-1` → `MKT-1`) |
| Модулю **впервые** задали ключ | его задачи переходят из ряда проекта в ряд модуля, номера новые, по порядку старых |
| Ключ у модуля убрали | задачи обратно в ряд проекта, номера новые |
| Модуль удалили | его задачи в ряд проекта, номера новые |
| Задали или убрали ключ проекта | меняется подпись ряда проекта (в том числе возврат к `TASK`), задач модулей не касается |
| Удалили задачу | её номер **не возвращается** и никому не достаётся |

«Ряд» это нумерация: у проекта один ряд, у модуля с ключом свой.

### 4.4 Пример

Проект «Сайт» с ключом `PLX`, модуль `SEO` (ключ `SEO`), модуль «Дизайн» (без ключа).

1. Создали две задачи без модуля: `PLX-1`, `PLX-2`.
2. `PLX-2` назначили в модуль SEO → она стала `SEO-1`. `PLX-2` больше не существует.
3. Создали ещё задачу без модуля: `PLX-3`.
4. `SEO-1` перенесли в «Дизайн» (ключа нет) → ряд проекта, новый номер: `PLX-4`.
5. Эту `PLX-4` вернули в «без модуля» → ряд тот же, id **не меняется**: `PLX-4`.
6. Ключ `SEO` переименовали в `MKT`: все задачи SEO теперь `MKT-n`, номера те же.
7. Модулю «Дизайн» (в нём 3 задачи) впервые задали ключ `DSN`: сначала окно «У 3 задач изменятся id», потом задачи становятся `DSN-1`, `DSN-2`, `DSN-3` (в порядке старых номеров).

### 4.5 Как это хранится

- В задаче лежат её **ряд** (проект или модуль с ключом) и **номер**. Префикс берётся при показе из текущего ключа ряда, поэтому переименование ничего не пересчитывает.
- Ряд модуля хранится как ссылка на модуль с запретом удалять модуль, пока в ряду есть задачи. Удаление модуля сначала переносит задачи в ряд проекта.
- Счётчик номеров у проекта (уже есть) и у модуля (новый). Он только растёт.
- **История прежних id:** при каждой смене ряда прежний id записывается (ключ, номер, ряд). В интерфейсе пока не используется.
- **Миграция:** всем существующим задачам ряд = их проект, номера те же. `WEB-141` остаётся `WEB-141`, демо-данные и эталонные скриншоты не меняются.

### 4.5.1 Как это сделано (этап П4)

- **Сервер.** `PATCH /modules/{id}` принимает `key`; проверки и перенос задач в `routes/modules.rs` (`ensure_key_free`, `move_series_for_key`), сама смена ряда в `db::tasks` (`move_to_series`, `set_module`, `move_all_to_series`). Модуль задачи теперь меняет только `set_module` (из `tasks::Patch` поле убрано), потому что от модуля зависит ряд. Всё под блокировкой проекта.
- **Клиент.** Поле «ключ» стоит в карточке модуля в свободном месте строки «ответственный, с, по» (справа внизу), в покое страница «Модули» отличается от эталона на 0,04% пикселей. Сохраняется по Enter или уходу из поля. Подсказка в пустом поле показывает, чем подписаны задачи сейчас (ключ проекта или `TASK`). Окно «У N задач изменятся id. Продолжить?» (`features/projects/IdChangeDialog.tsx`) показывается, если в модуле есть задачи; при смене ключа проекта в «Настройках проекта» оно ложится поверх этого окна, число считается по задачам в ряду проекта. Esc закрывает только верхнее окно (`useDialogFocus` ведёт стопку открытых окон).
- **Таблица.** Сортировка по столбцу ID идёт по ключу, потом по номеру (`lib/task-ids.ts`).
- **Проверки.** `crates/api/tests/keys.rs`: пример из 4.4 по шагам, правила ключей, снятие и возврат ключа (нумерация модуля продолжается), удаление модуля, номера не возвращаются, параллельные запросы, правило по всей базе (`assert_series_rule`: ряд задачи это её модуль, если у модуля есть ключ, иначе проект; видимые id в проекте не повторяются). E2E: `tests/visual/keys.spec.ts`.

### 4.6 Чего не делаем (решено)

- **Возврат прежнего номера** при переносе туда-обратно: задача получает новый номер. История хранится так, что добавить это можно позже.
- **Защита от повторного занятия старого ключа:** если переименовали `WEB` в `SITE` и потом назвали другой модуль `WEB`, его первая задача `WEB-1` не та, что `WEB-1` из старой переписки. Принято.
- **Лента** не переписывается: старые строки («WEB-141 перемещена») остаются как история, даже если ключ потом переименовали.
- Одинаковые id в разных проектах (`TASK-12` в нескольких) не отслеживаются. Принято.

### 4.7 Гонки

Если два человека меняют одно и то же одновременно, **побеждает последний**. Состояние остаётся согласованным (задача не окажется «в модуле без ключа»). Единственное исключение: два модуля в проекте с одним ключом. Второй получит ошибку «ключ уже есть в этом проекте» (для `TASK` текст пояснит, что он используется по умолчанию).

## 5. Права и безопасность

- **Проверка членства на каждом адресе сервера.** Когда запрос касается задачи, колонки, модуля, документа и т.п., сервер по самой записи определяет проект и проверяет, что человек в нём состоит. Это главное требование: обойти интерфейс программой для запросов (Postman, скрипт) можно с любым настоящим аккаунтом, и только отказ сервера защищает чужой проект.
- Тот, кто не состоит в проекте, получает такой же ответ «не найдено», как если бы проекта не было, чтобы не раскрывать его существование.
- События живых обновлений получают только участники проекта.
- **Тест «обход всех адресов».** У сервера есть машинный список всех адресов (по нему строится документация и типы клиента). Тест сам берёт каждый адрес, подставляет данные чужого проекта и вызывает от имени человека, которого в проекте нет. Если адрес отвечает данными вместо «не найдено», тест падает. Забытую проверку в новом адресе он тоже поймает. Открытые всем адреса (вход, свой профиль, список проектов) перечислены в тесте явно.
- **Защита «по умолчанию закрыто».** Запросы к базе о данных проекта сами принимают пользователя и отбирают только доступное: забыть проверку в таком запросе труднее, чем сделать. Каждый адрес сервера в тесте обязан быть помечен «открытый», «только про меня» или «внутри проекта»; адрес без пометки делает тест красным.
- **Все списки отдают только доступное:** проекты, документы, ссылки, лента, файлы, вложения. Проверяется негативными тестами на каждый вид данных: чужой проект нельзя ни прочитать, ни изменить, ни удалить, чужие файлы нельзя скачать, чужие события не приходят.
- **Уровень защиты.** Безопасность это требование: приложение будет работать за рамками одной команды, поэтому формулировка «для доверенной команды достаточно» неверна. Мои тесты проверяют только то, что придумал я. Независимого аудита у нас нет, и я его заменить не могу. Перед тем как пускать в приложение людей, которые друг другу не доверяют, нужна внешняя проверка. Я могу подготовить для неё описание угроз и прогнать автоматические проверки зависимостей (`cargo audit`, `npm audit`).
- **Вход (решения владельца):**
  - ограничение числа попыток входа: **не делаем** (принятый риск: пароль можно подбирать без пауз);
  - срок токена доступа (до 12 часов): **не сокращаем** (принятый риск: украденный токен действует весь день);
  - сообщения при неверном входе не должны выдавать, есть ли такой аккаунт: проверю и поправлю, если выдают.
- **Что откладываем вместе с «командой»:** список аккаунтов сейчас виден каждому вошедшему (имена и e-mail), и поиск по e-mail при приглашении подтверждает, что аккаунт существует. Для людей, которые не должны знать друг о друге, список надо ограничить теми, с кем есть общий проект, а ответ на приглашение сделать нейтральным. Решаем позже, вместе с «командой».
- **Вики:** все адреса вики проверяют доступ через одну общую функцию. Сейчас она пускает любого вошедшего, позже (с «командой») начнёт проверять членство в команде. **[моё предложение]**

## 6. Существующие данные (миграция)

- Все три демо-проекта остаются, их id задач не меняются.
- **Участники.** Все нынешние пользователи становятся участниками всех существующих проектов сразу, без приглашений. Глобальные админы становятся администраторами проектов, остальные участниками.
- Документы и ссылки уходят в первый проект.
- Миграции этапов 1 и 2 пишутся вместе с **обратными**. Откат коммитов базу не откатывает.
- Боевую базу мигрируешь ты, **перед этим нужен бэкап**: у меня нет доступа к твоему серверу.

## 7. Что в эту работу не входит

**Отложено на будущее:**
- Создание аккаунтов самими людьми (регистрация, авторизация).
- Приглашения письмом на почту.
- **Уровень «Команда» над проектами** с общей вики команды. Тогда человек видит вики своей команды (а твоё «общая из проектов, в которых я состою» станет возможным) и только свои проекты. Сейчас один сервер = одна команда, поэтому отдельное понятие не нужно. Что решим при его появлении: можно ли быть в нескольких командах (скорее да), кто создаёт команды (любой), видны ли члены только в своих проектах (да), роли команды, приглашение сначала в команду, список аккаунтов и библиотека файлов по команде.

**Не нужно:**
- Удаление проектов (только архив).
- Перенос задач между проектами.
- Роли, кроме двух (нет «наблюдателя»).
- Общие ссылки на все проекты.
- Превращение id задач в тексте в кликабельные ссылки.
- Одновременное посимвольное редактирование (то, что есть сейчас, достаточно).
