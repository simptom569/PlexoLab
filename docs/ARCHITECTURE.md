# Архитектура PlexoLab

```
Windows-клиент (Tauri 2 + React)  --HTTPS/WSS-->  Rust-бэкенд (axum)  -->  PostgreSQL
                                                         |
                                                         +--> диск: загруженные файлы
```

Клиент — один `.exe`-установщик. Данные лежат на сервере. При первом запуске клиент спрашивает адрес сервера и логин, дальше открывается сразу.

## Структура репозитория

```
/
  CLAUDE.md
  design/                     эталон, только чтение
  docs/
  server/                     Rust-бэкенд (cargo workspace)
    Cargo.toml
    crates/
      api/                    axum: роуты, middleware, WebSocket
      domain/                 типы и бизнес-правила без зависимости от axum
      db/                     sqlx-запросы, миграции в migrations/
    migrations/
    src/bin/seed.rs           демо-данные для разработки (из seed() макета)
  app/                        клиент
    package.json              React + TypeScript + Vite
    src/
      styles/styles.css       копия design/styles.css, не править
      components/             кнопки, чипы, аватары, карточки, поповеры ...
      features/board|backlog|modules|releases|wiki|docs|activity|links/
      lib/api/                клиент API, типы из OpenAPI
      lib/markdown/           порт design/reference/markdown-engine.js
    src-tauri/                оболочка Tauri 2
  tests/visual/               Playwright: сравнение со скриншотами эталона
  deploy/                     systemd-юнит, пример Caddyfile, postgresql.conf
```

## Бэкенд

- Крейты: `axum`, `tokio`, `sqlx` (postgres, uuid, time, migrate, runtime-tokio-rustls), `serde`, `tower-http` (cors, trace, compression), `argon2`, `jsonwebtoken`, `uuid`, `time`, `tracing`, `tracing-subscriber`, `utoipa` + `utoipa-axum`, `tokio-tungstenite` через встроенный ws axum, `thiserror`, `anyhow`.
- Конфигурация через переменные окружения: `DATABASE_URL`, `JWT_SECRET`, `BIND_ADDR`, `DATA_DIR` (файлы), `MAX_UPLOAD_MB` (лимит файла), `RUST_LOG`.
- Вход по e-mail и паролю (`argon2id`), токен доступа JWT (живёт 12 часов) + refresh-токен в базе (30 дней). Пользователей создаёт администратор из командной строки (`server user add`), публичной регистрации нет.
- Все ручки под `/api/v1`, формат JSON, ошибки в виде `{ "code": "...", "message": "..." }`.
- Живые обновления: `GET /api/v1/ws` (WebSocket). После каждого изменения сервер рассылает событие всем подключённым клиентам (внутри процесса, канал `tokio::sync::broadcast`). Редис и брокеры не нужны, сервер один. Токен клиент присылает первым сообщением, а не в адресе (адреса попадают в журналы); протокол и список событий в `docs/DATA-MODEL.md`.
- Загрузка файлов: `multipart`, на диск в `DATA_DIR/files/<uuid>`, метаданные в БД, лимит размера задаётся настройкой (по умолчанию 25 МБ).
- OpenAPI-схема отдаётся на `/api/v1/openapi.json`. Из неё генерируются TypeScript-типы клиента (`openapi-typescript`), чтобы типы не расходились.
- Здоровье: `GET /healthz`.

## Клиент

- Vite + React + TypeScript. Маршрутизация простая (состояние `page`), отдельная библиотека не нужна: экранов восемь, как в боковом меню.
- Данные: TanStack Query. Изменения применяются оптимистично (карточка сразу встаёт на место), при ошибке откатываются.
- WebSocket: события инвалидируют нужные запросы (`task.updated` → обновить доску и карточку).
- Локальные настройки (тема, вид, фильтры, «Отображение», адрес сервера): `tauri-plugin-store`. Токен хранить в системном хранилище учётных данных (крейт `keyring` через команду Tauri), не в открытом файле.
- Перетаскивание: `dnd-kit`, с заглушкой (drop placeholder) как в макете: `DragOverlay` для «летящего» элемента, на месте падения пунктирный блок `.ph` высотой с переносимый элемент (`.ph-col` для колонок, `.brow-ph` для строк бэклога, `.cal-ph` в календаре), исходный элемент приглушён классом `.drag`, колонка-цель `.col.over`. В макете этот эффект сделан нативным HTML5 drag and drop, поведение (какую сторону карточки выбирает указатель, когда заглушку не показывать) описано в `docs/SPEC.md`.
- Редактор markdown и холст: свои, без библиотек, см. `docs/EDITOR-AND-CANVAS.md`.

## Tauri 2

- Цель сборки: Windows, `nsis`. Режим установки WebView2 — через встроенный или скачиваемый загрузчик (см. настройку `webviewInstallMode` в документации Tauri 2). Проверь актуальные названия в документации, версии меняются.
- Название: `productName` и заголовок окна — «PlexoLab». Иконка: `npm run tauri icon <путь>` по файлу из `CLAUDE.md` (раздел «Бренд»); пока пути нет, иконки по умолчанию.
- Окно: минимальный размер около 900×600, остальное как в макете (макет адаптивный). Нативная рамка окна, дизайн повторяем внутри окна.
- Один экземпляр приложения (`tauri-plugin-single-instance`), запоминание размера окна (`tauri-plugin-window-state`).
- Обновления по желанию (`tauri-plugin-updater`) — отдельным этапом.

## Развёртывание на сервере 1 ядро / 1 ГБ

Сервер уже занят другим сервисом (около 40% памяти). Ориентир по памяти, оценки без измерений:

| Компонент | Память |
|---|---|
| Существующий сервис и система | около 400 МБ |
| PostgreSQL (урезанные настройки) | 100–200 МБ |
| Бэкенд на Rust | 20–60 МБ |
| Caddy или другой прокси | 20–40 МБ |
| Итого | около 600–700 МБ |

Что сделать:

1. **Postgres.** В `postgresql.conf` примерно: `shared_buffers = 64MB`, `effective_cache_size = 256MB`, `work_mem = 4MB`, `maintenance_work_mem = 32MB`, `max_connections = 20`. Пул соединений `sqlx` не больше 5.
2. **Swap.** Включить 1–2 ГБ swap как страховку от OOM-killer.
3. **Порт.** Если существующий сервис слушает 443, бэкенд на нём не поднимется. Проверь `ss -tlnp`. Варианты: другой порт (например 8443), отдельный поддомен с проксированием по SNI, либо доступ только через VPN/WireGuard без публичного порта.
4. **HTTPS.** Клиент должен ходить по HTTPS. Caddy выдаёт сертификаты Let's Encrypt автоматически, нужен домен. Без домена можно самоподписанный сертификат, но тогда клиент придётся настроить его принимать, это отдельная возня.
5. **Запуск.** Бэкенд как systemd-служба (`deploy/plexolab.service`). Собирать бинарник на своём компьютере или в CI, на сервер класть готовый файл. На 1 ГБ `cargo build` не соберётся.
6. **Бэкапы.** Ежедневный `pg_dump` в сжатый файл + копия папки `DATA_DIR/files`, хранить 7–14 копий, раз в неделю проверять восстановление.
7. **Мониторинг.** Логи через `journalctl`, ручка `/healthz`, лог времени ответа. Нагрузочный тест (`k6`) на 20–30 одновременных пользователей перед выдачей команде.
