# Дорожная карта PlexoLab

Работа идёт по этапам, строго по порядку. Каждый этап заканчивается проверкой по критериям «Готово, когда», к следующему переходят только после неё. Где у этапа есть строка «Читать», в ней документы с подробностями.

**Состояние на 2026-10-30.** Сделаны этапы 0–8, П1–П5, К1–К3, Р1–Р2 и Н1–Н5. Впереди этап 9 (упаковка Tauri: сделана часть, остаток описан в самом этапе) и этап 10 (развёртывание сервера).

---

## Этап 0. Каркас репозитория

**Готово, когда:** `cargo build` проходит, `/healthz` отвечает, `npm run tauri dev` открывает пустое окно, первый коммит сделан.

## Этап 3. Доска: API и интерфейс

Читать: `docs/SPEC.md` (разделы «Общее», «Доска»), `docs/COMPONENTS.md` (доска, панель задачи).

- при переносе на месте падения виден пунктирный placeholder (для карточек, колонок, строк бэклога и дня календаря), возврат на то же место его не показывает, снимки состояний сравниваются с макетом;
- календарь: перенос задачи в другой день меняет срок;
- в панели задачи работают все поля, подзадачи, комментарии, создание метки по Enter;
- действия появляются в таблице `activity`.

Решение владельца 2026-10-21: до упаковки (этапы 9 и 10) сделать проектный уровень. Полное утверждённое описание: `docs/PROJECTS.md`, читать его целиком перед каждым из этапов П1–П5. ### Этап П1. Ключи задач: схема и миграция

**Готово, когда:** все существующие тесты сервера и клиента проходят без правок ожиданий, `WEB-141` остаётся `WEB-141`, новые тесты проверяют ряд и номер при создании задачи, обратная миграция возвращает схему и данные.

### Этап П2. Участники, приглашения, права

**Готово, когда:** тест-обход и негативные тесты на каждый вид данных проходят, нынешние пользователи при миграции стали участниками всех проектов, в сайдбаре только мои проекты, существующие тесты проходят.

### Этап П3. Проекты в интерфейсе

**Готово, когда:** эталонные скриншоты сайдбара без наведения совпадают с макетом, создание проекта, приглашение, принятие, выход, архив и настройка меток работают у двух клиентов.

### Этап П4. Ключи в модулях

**Готово, когда:** сценарий из раздела 4.4 PROJECTS.md проходит как e2e-тест, ряд задачи всегда соответствует правилу (проверочный тест по всей базе), параллельные запросы не ломают нумерацию.

### Этап П5. Документы, ссылки и лента по проектам

**Готово, когда:** у каждого проекта свои документы, ссылки и лента, тест-обход проходит для новых данных, существующие e2e-тесты обновлены под проект.

## Работа без связи, уведомления, поиск (этапы Н1–Н5)

Решение владельца 2026-10-26. Полное утверждённое описание: `docs/OFFLINE-NOTIFY-SEARCH.md`, читать его целиком перед каждым из этапов Н1–Н5. Порядок: Н1, Н2, Н3, Н4; Н5 вместе с этапом 9. Каждый этап: сначала тесты и серверная часть (если есть), потом клиент.

### Этап Н1. Режим «только просмотр» при обрыве связи

**Готово, когда:** тесты с выключением сети (Playwright) показывают полоску через 3 секунды, закрытые правки, содержимое на месте, возврат связи снимает полоску и перечитывает данные; неотправленный текст страницы после возвращения связи уходит; существующие тесты проходят.

### Этап Н2. Не потерять правки: копия при конфликте и защита при закрытии

**Готово, когда:** e2e-тест с двумя клиентами (правка, обрыв, уход со страницы, чужая правка тех же строк, возврат связи) оставляет оригинал с чужой версией и копию с правками первого; при закрытии с неотправленным текстом приложение сначала пробует отправить, потом спрашивает.

### Этап Н3. Уведомления и @упоминания

**Готово, когда:** каждая ручка с тестом на реальном Postgres, посторонний не видит и не может упомянуть чужих, у двух клиентов уведомление приходит сразу, счётчик и «прочитано» работают.

**Готово, когда:** поиск не показывает чужие проекты (тест), находит по куску названия и по id, окно работает с клавиатуры.
