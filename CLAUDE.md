# PlexoLab: правила проекта

## Бренд

- **Название приложения: PlexoLab.** Оно в заголовке окна, в установщике, в `productName` Tauri, в `<title>` страницы, в боковом меню (рядом с иконкой, подпись «Рабочее пространство»). Старое рабочее название «Командная доска» и «Разработка» не использовать.
- **Иконка приложения.** Файл иконки владелец проекта положит сам. Путь к ней записан здесь:

  ```
  ICON_PATH:  Найди icon.png в текущей директории папка design <- владелец вписывает путь (желательно PNG 1024×1024 с прозрачным фоном)
  ```

  Пока путь пустой, **не придумывай и не рисуй логотип**. В боковом меню оставь пунктирную заглушку `.brand-slot` из макета (32×32, скругление 10px), а иконки Tauri оставь по умолчанию.
- Когда путь указан: подключи файл в боковое меню вместо заглушки (`<img>` 32×32, `border-radius:10px`, `object-fit:contain`), положи его в `app/src/assets/`, и сгенерируй иконки сборки командой `npm run tauri icon <ICON_PATH>` (создаёт `.ico`, `.icns` и PNG для `app/src-tauri/icons/`). Иконка окна и установщика берётся оттуда.
- Идентификатор приложения Tauri (`identifier`, вида `com.xxx.plexolab`) уточни у владельца, не выдумывай домен.

## О проекте

Десктоп-приложение для небольшой команды разработки: канбан-доска, бэклог, модули, релизы и вехи, вики с файлами, документы (страница и холст), активность, ссылки команды. Интерфейс уже нарисован в макете. Задача проекта: повторить его **один в один** и оживить настоящим бэкендом.

## Стек (не менять без согласования)

- **Бэкенд:** Rust, `axum`, `tokio`, `sqlx` (PostgreSQL, миграции `sqlx migrate`), `serde`, `tower-http`, `argon2`, `jsonwebtoken`, `tracing`, `utoipa` (OpenAPI).
- **Клиент:** Tauri 2 (Windows-приоритет, сборка NSIS `.exe`) + **React + TypeScript + Vite**.
- **Стили:** обычный CSS. `design/styles.css` копируется в проект **как есть**. Никакого Tailwind, MUI, Bootstrap, styled-components.
- **Состояние:** Zustand для локального UI-состояния, TanStack Query для данных сервера.
- **Допустимые библиотеки без собственного оформления:** `dnd-kit` (перетаскивание), `date-fns`, `zod`, `openapi-typescript` (типы из OpenAPI бэкенда). Любую другую библиотеку, которая тянет свои стили или готовые компоненты интерфейса, сначала согласуй.
- **Шрифты:** Manrope (400/500/600/700) и JetBrains Mono (400/500). Подключай локально через `@fontsource/*`, не через Google Fonts: приложение должно работать без интернета до первого запроса к серверу.

## Эталон интерфейса

Источник правды по внешнему виду и поведению лежит в `design/`:

- `design/Main.dc.html` — макет. Это формат внутреннего редактора, в браузере сам по себе не откроется. Читай его как исходник: разметка внутри `<x-dc>`, стили в `<style>`, логика в классе `Component` (`seed`, `vBoard`, `vPanel`, `mdKey`, и т.д.).
- `design/styles.css` — весь CSS макета без изменений.
- `design/screenshots/` — скриншоты каждого экрана в светлой и тёмной теме (уже в репозитории, список экранов в `design/screenshots/README.md`).
- `design/reference/markdown-engine.js` — чистые функции разбора markdown из макета (блоки, строки внутри, подсветка), их нужно портировать на TypeScript без изменения поведения.

### Жёсткие правила

1. Цвета, радиусы, отступы, размеры шрифтов, тени, анимации бери только из `design/styles.css` и из инлайн-стилей разметки макета. **Не придумывай свои значения и не «улучшай» дизайн.**
2. Имена CSS-классов оставляй такими же, как в макете (`.card`, `.chip`, `.col`, `.seg`, `.pop`, `.drawer`, ...). Корневой контейнер приложения — `<div class="app">` или `<div class="app dark">`.
3. Все цвета через CSS-переменные (`--bg`, `--surface`, `--accent`, ...). Светлая и тёмная тема переключаются классом `dark` на `.app`.
4. Перед тем как делать экран, **открой в `design/Main.dc.html` нужный блок разметки и методы логики** (см. `docs/COMPONENTS.md`) и перенеси структуру DOM, классы, инлайн-стили и тексты дословно. Тексты интерфейса на русском, как в макете.
5. Не добавляй экраны и функции, которых нет в макете. Если чего-то не хватает или макет противоречит сам себе — остановись и спроси.
6. После каждого экрана делай скриншот в Playwright (Chromium, окно 1440×900, обе темы) и сравни с `design/screenshots/`. Отличия исправляй сразу. Допуск по пикселям задан в `tests/visual`.
7. Доступность макета сохраняй: `aria-*`, `role`, видимый фокус, `sr`-подписи, клавиатурное управление в дереве, меню и редакторе.

## Что в макете демонстрационное, а что настоящее

- «Сегодня» в макете зафиксировано как `2026-10-18`, текущий пользователь `Л`. В приложении используй реальную дату и текущего пользователя из токена.
- Данные из `seed()` — только пример. В базу они попадают через сид-скрипт для разработки (`cargo run --bin seed`), а не зашиты в клиент.
- Фильтры, вид (доска/список/...), «Отображение» карточки, тема, открытая страница — настройки конкретного пользователя на конкретном компьютере. Храни их локально (Tauri store), на сервер не отправляй.

## Рабочий процесс

- Работай этапами из `docs/PLAN.md`, один этап за раз. В конце этапа покажи: что сделано, как проверить, что не сделано. Не переходи дальше без подтверждения.
- Бэкенд: сначала миграция и тесты, потом ручки. Каждая ручка с автотестом на реальном Postgres (`sqlx::test`).
- Клиент: сначала компонент и его состояния, потом подключение к API.
- Коммиты небольшие, сообщения на русском в формате `тип: что сделано`.
- Не трогай `design/` — это эталон, он только для чтения.

## Ограничения сервера

Продакшен-сервер: 1 ядро, 1 ГБ RAM, уже работает другой сервис. Бэкенд и Postgres вместе должны укладываться примерно в 300 МБ. Подробности и настройки в `docs/ARCHITECTURE.md`. Не добавляй тяжёлые зависимости и фоновые процессы без согласования.
